# UFO — Autonomous CFO (Red Hat OpenShift AI & Commerzbank Collabothon 2026)

## THE PROBLEM
Small and medium business owners often don't have CFOs. People don't excel at predictions, especially those who lack experience in finance. Our solution helps small teams see how a decision will affect their cash before they make it.

## YOUR SOLUTION
The core idea is simplicity: our app is pretty straightforward, and from the very beginning, it guides the user through each step to get a cash flow forecast. Since a small or medium enterprise owner can range from a student with a startup to a senior who wants to start a business, we've made the website accessible to everyone. Users can easily import a CSV or (planned) connect their bank account, and easily get a forecast generated by multiple models.

## THE WORKING PROTOTYPE
Users can easily import a CSV of any type as long as it has the minimum necessary fields; the field names don't matter, as users can adjust them on import. They can add records manually later.
Today, users can get a detailed analysis and an extensive forecast of their cash flow. After that, they can analyze a very comprehensive graph with convenient features. They can get an LLM summary and analysis of the forecast, as well as historical data or a chosen time period.
Users can simulate "What-if" scenarios so that they can see how a financial decision might affect their balance. There are also recommendations from the LLM, including the ability to suggest a loan if the balance becomes dangerously low and the profit is negative.
There is always an option to ask the chatbot, Greg, any question about the app or their financial state.

## BEHIND THE BUILD
Forecast: The algorithm automatically chooses the model that fits the data best based on historical data, selecting one of the following: a classic deterministic model, our own neural network trained on a huge dataset, or existing imported models from the StatsForecast library (ETS, ARIMA, THETA). We decided not to use an LLM for the forecast, since it could hallucinate. We decided to train our own neural network on a large dataset from Hugging Face that fits the goal. While it was training, we found the aforementioned open library and decided to use more models, choosing the one with the smallest error depending on the data. We also used an LLM running on OpenShift servers with NeMo Guardrails so that the chatbot sticks to the topic. We implemented CI/CD that tests our solution and deploys it to OpenShift upon merging to main.
Among the tools we used: Python, StatsForecast, Keras + TensorFlow, HTML, CSS, JS, NeMo Guardrails, Llama 3.2-3B deployed on OpenShift AI, KaggleHub, Hugging Face, Ruff, uv, and Git.

## CHALLENGES AND DISCOVERIES
Figuring out a new environment (OpenShift) and deploying a model on it; defining a scope that we would be able to implement in a limited time; analyzing the market and figuring out an idea that would truly matter; and a lack of sleep.
We discovered ways to analyze and estimate cash flows, new tools like OpenShift and StatsForecast, the caveats of the financial world, and how to organize teamwork.

## RESULTS AND NEXT STEPS
We ended up with a working full-stack prototype with a simple, minimalistic UI and a cash flow forecast with a relatively small error, allowing users to replace spreadsheets with a guided advisor. We ran unit tests and validated the models on various datasets, including part of a large dataset that the models had never seen and that was as close to real data as possible, comparing the results with actual cash flow.
Current limitations and roadmap: We want to implement the ability to connect to a user's bank to load records automatically, as well as the ability to connect to Commerzbank's tools so that our loan system can utilize them. We also want to implement a secure login system, a history of records with the ability to filter them by categories and dates, and potential integration into the banking system.

## Key Capabilities

1. **Flexible CSV Import & Column Mapping**
   - Supports `;`, `,`, and tab delimiters, EU/US number formats, ISO/`DD.MM.YY`/`YYYY-MM` dates, single signed `Amount` columns, or split Income/Expenses columns (e.g. `date,revenue_pln,expenses_pln`), automatic currency suffix inference, and inline `@ <rate> EUR/<CURR>` FX conversion.
   - Categorizes transactions into strictly **`Salaries`**, **`Taxes`**, or **`Other`**, keeping social-security and health-insurance funds out of `Taxes`.

2. **Two-Tier Adaptive Forecasting**
   - **Seasonal Monthly Planner (`>= 12` full months)**: Evaluates **Classic (Seller Method)**, **Own Model (Seq2Seq BiLSTM via pure NumPy)**, and **StatsForecast** (`AutoETS`, `AutoARIMA`, `AutoTheta`, and `Combo`) via walk-forward backtesting on up to the last 3 years, displaying the chosen method and selection notes in the UI alongside a pessimistic stress-test trajectory.
   - **Daily Fallback (`< 12` full months)**: Detects monthly/quarterly recurring bills, computes weekday non-recurring averages, overlays future manual operations, and projects 30/60/90-day daily balances.

3. **Tab-Isolated Stateful Sessions & Zero-Leakage Headers**
   - Every browser tab maintains an isolated in-memory ledger via `X-Greg-Session` backed by TTL/LRU eviction, and HTML/JSON/JS/CSS responses enforce `Cache-Control: no-store`.

## LLM Security

**Always on (in code):**
- `/api/chat` rejects client-supplied `system` messages, always injects Greg's own grounded system prompt, accepts only `user`/`assistant` turns of at most 4,000 characters, and keeps the last 12.
- The system prompt limits Greg to the business's finances and tells the model to treat CSV names and references as data. CSV-derived names are flattened to one short line before they are embedded.
- The CSV classifier sends transactions as JSON lines inside a `<transactions>` block marked as untrusted, and only accepts `Salaries`/`Taxes`/`Other` back.

**Topic gate (on whenever an LLM is configured):** before answering, Greg asks the model a one-word YES/NO question: is this message about the business's money? Off-topic requests (poems, jokes, code, general knowledge) get the same polite `422` refusal, and the UI drops them from history. If the gate call fails, the message goes through. Without imported data, the system prompt forbids inventing numbers.

**Grounded answers:** chat questions that mention dates or months (`2025-03-14`, `14.03.25`, `14 March`, `March 14, 2025`, `in May`, `05/2025`, German month names too) get a DATE LOOKUP section with that day's payments and start/end balance, or that month's category totals, biggest payers and lowest balance. Dates outside the data are reported as having no data. Chat also gets a short guide to the app's screens, so "how do I…?" questions are answered.

**NeMo Guardrails (optional, OpenShift AI 3.5+):** every chat message is screened by a DeBERTa prompt-injection classifier before it reaches the model. Blocked messages return `422` with a polite refusal; if the guardrails service is down, chat returns `503` unless `GUARDRAILS_FAIL_OPEN=true`.

```bash
oc apply -n my-first-model -f deploy/security/   # guardrails server, RBAC, egress NetworkPolicy
oc get nemoguardrails,svc -n my-first-model      # find the guardrails service name and port
```

Then set `GUARDRAILS_CHECK_URL` in [`deploy/configmap.yaml`](deploy/configmap.yaml) to `http(s)://<service>.my-first-model.svc.cluster.local:<port>/v1/guardrail/checks` and redeploy. The auth-enabled service listens on HTTPS (port 443), so the URL must start with `https://`; Greg trusts OpenShift's service CA from the pod's service account mount automatically.

`deploy/security/` is not applied by CI, because the `NemoGuardrails` CRD only exists once the TrustyAI component is enabled.
